# 编码规范

> 本规范为**语言无关**的通用规范，适用于所有编程语言。语言特有规则见 [Rust](rust.md)、[LaTeX](latex.md) 等文档。

## 注释规范

### 公共 API 文档注释
所有公开的函数、类、接口、字段必须写文档注释，说明功能、参数含义和返回值。

### 模块级文档
每个源文件或模块顶部说明其职责以及与其他模块的关系。

### 内部注释
函数内部的关键逻辑步骤、边界条件处理和设计决策必须写中文注释，说明**为什么这么做**而非做了什么。

## 代码风格

- 使用语言自带的格式化工具统一代码风格
- 使用静态分析工具确保无 warning
- 减少不必要的变量拷贝，优先通过引用传递
- 模块/文件职责单一，按功能拆分，避免大而全的模块

### 日志规范

所有应用必须使用结构化日志框架，禁止用基础打印输出替代日志。

| 日志级别 | 使用场景 | 说明 |
|---------|---------|------|
| `error` | 不可恢复的错误、异常退出 | 替代未经框架的错误输出 |
| `warn` | 可恢复的异常、降级处理 | 配置缺失使用默认值 |
| `info` | 关键操作节点、状态变化 | 初始化完成、操作成功 |
| `debug` | 开发调试细节 | 函数调用、文件路径、过程数据 |
| `trace` | 极细粒度跟踪 | 循环迭代、内部状态变化 |

**核心原则**：
- 所有模块应按上述级别添加日志，以覆盖关键操作路径和异常路径
- 日志输出格式应由框架统一控制，不允许手动拼接日志字符串
- 用户界面的正常输出（列表、结果提示等）使用标准输出，不以日志替代

### 代码复用原则

重复是 warning 和一致性问题的常见根源：

| 场景 | 正确做法 | 反例 |
|------|---------|------|
| 多个模块需要相同功能 | 提取到公用模块/工具类 | 各模块独立实现导致重复代码 |
| 同一功能有多个实现 | 删除重复，统一调用 | 一个功能写多份导致一部分变死代码 |
| 已废弃的函数/字段 | 直接删除，不用 suppress 掩盖 | 加上 lint 抑制注解留下垃圾代码 |

**核心原则**：
- 不要使用 lint 抑制机制掩盖 warning，应直接删除未使用的代码或接入调用
- 每个公开函数/方法至少有一个调用者，否则说明设计不合理
- 模块单一职责：一个模块只做一件事，多个模块都需要的事提到公用模块中
- 数据与操作分离：公用的工具函数放在独立的工具模块中，不耦合在业务模块里

# 测试规范

## 单元测试

测试文件放在被测试模块内部，与源代码保持同一目录结构。

### 测试覆盖要求

- **正常路径（happy path）**：确保核心功能按预期工作
- **边界条件**：空值、极值、缺失字段、空集合等
- **错误路径**：格式错误、非法输入、权限不足等

### 修改代码后检查测试

修改功能代码后，必须审查现有测试用例：
- 如果测试名所描述的行为已不再适用或已变更，需同步更新测试内容
- 如果新增了功能，需添加对应的测试覆盖
- 不要保留与实际逻辑不相符的误导性测试名

### 测试注释

每个测试用例前必须写文档注释，使用语言自带的文档注释语法，用中文说明测试目的和验证要点。
注释描述的是"该测试验证了什么"，而非"测试名是什么"。

### 测试命名

测试用例使用 `test_<模块>_should_<预期行为>` 格式：

```
test_parse_should_handle_standard_input
test_parse_should_fail_on_empty_input
test_parse_should_return_error_for_invalid_format
```

## Mock 策略

| 需 mock 的场景 | 推荐做法 |
|--------------|---------|
| 文件系统操作 | 使用临时目录（如 `tempfile` 或 `tmpdir`）或内存文件系统 |
| 外部进程调用 | mock 外部命令调用，返回预设结果 |
| 配置读取 | 直接从字符串/字典反序列化，无需真实配置文件 |

## 测试金字塔

- **单元测试**（大量）：核心逻辑全覆盖，速度快
- **集成测试**（少量）：模块间交互流程、外部依赖集成
- 使用语言的测试框架运行所有测试（如 `cargo test`、`pytest`、`jest`）
